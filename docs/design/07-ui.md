| | |
| --- | --- |
| Milestone | M1 |
| Status | **Designed**, with one prototype-dependent behaviour (passive focus/window flags on Wayland, §7) |

## 1. Scope

Everything the user sees and touches: the passive result window, the application window (status, explicit paste,
settings entry), the settings pages, the consent flow and the optional tray item. It contains no acquisition,
network or persistence logic — it renders coordinator state and forwards user intent.

## 2. Responsibilities

- Render `coordinator::ResultView` in the result window, in plain text, with the destination and actions.
- Own all user-visible wording and localization.
- Provide the explicit paste field, the clipboard action and the pause/resume control.
- Run the consent flow and hand the confirmed record to `SettingsStore`.
- Present capability status without overclaiming coverage.
- Support keyboard navigation, screen readers, system theme, font scaling and reduced motion.
- Remain fully usable with no tray and no global shortcut.

## 3. Non-responsibilities

- No selection access, no provider selection policy, no consent *decision* (it records the user's), no retry
  timers, no persistence, no logging of user text.

## 4. Structure

```text
src/ui/
  qml/
    AppWindow.qml              # normal window: state, pause/resume, paste field, open settings
    ResultWindow.qml           # passive result popup
    SettingsWindow.qml         # pages (see §9)
    components/
      ConsentSheet.qml         # destination + consequences + confirm/cancel
      StatusBanner.qml         # backend unavailable, secret store notice, save failure
      ResultText.qml           # plain-text result with selection + copy
      KeyValueRow.qml, PageSection.qml, FieldLabel.qml
    theme/
      Tokens.qml               # semantic tokens (light/dark/high-contrast values)
      qmldir
  controllers/
    ResultController.{h,cpp}   # wraps coordinator::ResultView for QML
    AppStatusController.{h,cpp}
    PasteController.{h,cpp}
    SettingsController.{h,cpp}
    ConsentController.{h,cpp}
  main_window.cpp              # window creation, flags, anchoring, placement
```

Registration: one `qmlRegisterSingletonInstance` per controller (`SnipLingo.Result`, `SnipLingo.App`,
`SnipLingo.Paste`, `SnipLingo.Settings`, `SnipLingo.Consent`). Controllers expose read-only properties with
`NOTIFY` signals and `Q_INVOKABLE` commands; QML never calls D-Bus, HTTP or the filesystem.

## 5. Controllers

```cpp
class ResultController : public QObject {   // QML: SnipLingo.Result
    Q_OBJECT
    Q_PROPERTY(bool visible READ visible NOTIFY changed)
    Q_PROPERTY(QString translatedText READ translatedText NOTIFY changed)
    Q_PROPERTY(QString originalText READ originalText NOTIFY changed)
    Q_PROPERTY(QString providerLabel READ providerLabel NOTIFY changed)
    Q_PROPERTY(QString stateKey READ stateKey NOTIFY changed)   // "loading" | "streaming" | "done" | "error"
    Q_PROPERTY(QString errorKey READ errorKey NOTIFY changed)   // ErrorCode → translation key
    Q_PROPERTY(bool canRetry READ canRetry NOTIFY changed)
public slots:
    void copyResult();      // QClipboard::setText, only from an explicit user action
    void dismiss();         // → coordinator::dismissResult()
    void retry();           // → coordinator::retryLastRequest()
    void toggleOriginal();
signals:
    void changed();
};
```

Rules:

- `stateKey`/`errorKey` are keys, not sentences; `qsTr()` resolves them in QML. Unknown codes fall back to a
  generic message plus the code name (never the raw `detail`, which may contain paths or HTTP strings but no user
  text — still, `detail` is logged only).
- `copyResult()` is the only clipboard write in the application. It requires window focus (see §7).
- No streaming repaint per token: the controller coalesces deltas on a 50 ms timer and emits `changed()` at most
  20 times per second; this keeps QML layout work bounded without asking the provider to behave differently.

## 6. Windows

| Window | Type | Flags | Shown when |
| --- | --- | --- | --- |
| `AppWindow` | normal toplevel (`Qt::Window`) | none special | user opens the app, or a notice needs attention; also the entry point on desktops without a tray |
| `ResultWindow` | passive toplevel | `Qt::Tool`, `Qt::FramelessWindowHint`, `Qt::WindowStaysOnTopHint` (best effort), `Qt::WindowDoesNotAcceptFocus` while passive | a view state other than `Idle`/`Paused` arrives |
| `SettingsWindow` | normal toplevel, modal to nothing | — | user opens settings from either window or the tray |
| Tray menu | `QSystemTrayIcon` with SNI where available | — | optional; absence must not remove any control |

`AppWindow` contents, in order: automatic-mode state (enabled / paused / unavailable + backend name and its
stated limitation), pause/resume button, paste field with a translate button, optional clipboard action, then
links to settings and the diagnostic report. No preferences live here.

## 7. Result window behaviour

For automatic selections, show a small icon by default and expand the existing result window when the
pointer enters it. A click also opens the result. `selection.showResultImmediately` opens the full window
directly instead. Translation starts after the selection is resolved, subject to remote consent; hovering
only changes presentation. Explicit text and clipboard requests always open the full window. Each new
automatic selection resets the presentation to the configured mode.

**Focus and dismissal.** The collapsed icon requests no focus. The expanded result requests focus and dismisses
when it subsequently loses focus, allowing clicks to reach other windows without a global input listener or
pointer grab. This means expanding the result can move keyboard focus away from the source application.
Compositors may reject activation or leave focus unchanged when a non-focusable surface is clicked; those
cases do not provide a reliable outside-click notification. GNOME Wayland was observed to ignore the
non-focus hint for the collapsed window; XWayland avoided activation in the tested session.

**Anchoring.** For automatic selections the runtime samples the Qt pointer position on the selection event;
if that is unavailable, it uses a usable AT-SPI range rectangle. It prefers a position below and to the
right, flips to the other side when needed, and clamps to the selected screen's available geometry. A
keyboard selection may therefore use the pointer as an approximate anchor. Wayland compositors may ignore
client window positions. In addition, XWayland's pointer position may be stale while the pointer is over a
native Wayland surface, even if the compositor bridges that application's PRIMARY selection. Do not claim
the icon is reliably adjacent in that case. Explicit translations are centred on the pointer's screen.

**Content.** Plain text only (`TextEdit` with `QMimeData`-free, `textFormat: PlainText`); links are not
activated; the result scrolls after a maximum height; the provider label is visible in the footer; the original
text is collapsed behind a disclosure and shown in a monospace face when it contains no spaces and looks code-like
(heuristic limited to that, no script detection).

**Actions.** Copy (explicit), close, retry (error state only), toggle original, open settings, and a pause
control when the error concerns automatic mode. No action pastes into another application.

**States** (`../ui-ux-spec.md` §1.5): `loading` (skeleton, dismissable), `streaming` (accumulating text, caret),
`done`, `error` (cause key + hint key + actions), `consent` is never rendered in this window (it belongs to
`AppWindow`, so nothing is queued while consent is missing).

## 8. Consent flow

Triggered by `coordinator::consentRequired(destinationLabel, stale)`:

1. Open `AppWindow` (never the passive window) with `ConsentSheet` as an inline sheet.
2. Sheet content: destination label, the plain statement that every eligible selection will be sent to that
   destination automatically and may incur cost, the pause control, and the paste alternative. For a local
   endpoint, the sheet says no data leaves the machine but notes the app cannot verify a service's own behaviour.
3. `Confirm` ⇒ `SettingsStore::grantConsent(activeProvider)` ⇒ `coordinator::recheckConsent()`; automatic mode
   resumes on the next selection (never on the stored selection).
4. `Cancel` ⇒ nothing recorded; automatic remote sending stays off; the paste field keeps working.
5. Consent is per destination fingerprint (module 02 §7); changing endpoint re-opens this sheet with
   `staleConsent=true` wording.

## 9. Settings pages

One scrollable page per section, no nested tabs (`../ui-ux-spec.md` §3):

| Page | Fields | Notes |
| --- | --- | --- |
| Automatic mode | enabled, paused, backend (`auto` or a named backend), backend status, stability delay, character limit | shows the *stated coverage* sentence for the chosen backend; a "test with a selection" action reports only whether an event arrived |
| Provider | type, base URL, model, streaming, key entry, "test connection", destination label, consent state | key entry writes to `SecretStore` and clears the field; "test" sends one short synthetic sentence |
| Languages | source (`auto` or tag), target | locale-derived default, always editable |
| Privacy | what is observed, what is sent, pause, clear consent, clear session key, diagnostic report | text only, no telemetry controls because none exist |
| About | version, licenses, doctor output, issue links | doctor output is environment-only |

### Known environment constraint (measured)

The Qt 6.11 build used for the probe has **no AT-SPI accessibility bridge** (`libQt6Gui.so.6` contains no
`org.a11y` references). An application built against such a Qt cannot expose its own UI to assistive
technology, and the same build cannot be used to host an AT-SPI provider for tests. Any Qt chosen for the
product must be verified with `strings libQt6Gui.so.6 | grep -c org.a11y` (non-zero) plus a real screen
reader check before accessibility can be claimed; a self-built/conda Qt is not sufficient evidence.

## 10. Accessibility and localization

- Every control has an accessible name; the result text is a document role; the result window announces the
  destination and the first 200 characters once at completion, not on every delta (`../ui-ux-spec.md` §4).
- Full keyboard operation of `AppWindow` and `SettingsWindow`; visible focus ring; `Esc` closes sheets and
  settings; the result window honours `Esc` once focused.
- System theme via `QStyleHints::colorScheme()`; semantic tokens only; contrast targets from the UI spec; reduced
  motion honoured plus an explicit override.
- All strings via `qsTr()`; `translations/*.ts`; no string concatenation; language names shown as endonyms.

## 11. Threading

UI thread only. Controllers subscribe to coordinator/settings signals with auto-connections; no controller performs
blocking work. Long lists do not exist. The 50 ms delta coalescing timer is a `CancellableDelay`.

## 12. Errors and edge cases in the UI

| Situation | Presentation |
| --- | --- |
| Settings save failed | persistent `StatusBanner` in `AppWindow`: change not applied + retry |
| Secret store is session-only | `StatusBanner` in provider page and onboarding: key will be forgotten on exit |
| Backend absent/denied | `StatusBanner` with the reason and the paste alternative; automatic mode shows `unavailable` |
| Provider error | result window error state, destination named, retry + settings |
| No tray available | nothing changes functionally; `AppWindow` carries every control |
| Streamed text replaced by a newer selection | window content swaps without an animation; no stacking |

## 13. Dependencies and boundaries

Allowed: `05`, `02`, `03` (credential entry only), `04` (status/probe values), Qt Quick/QuickControls/qt_add_translations.
Forbidden: direct HTTP, direct D-Bus, direct file access, selection backend construction, provider construction.

## 15. Open questions

1. **Passive focus on Wayland (blocking for M1 acceptance):** does `Qt::WindowDoesNotAcceptFocus` plus mapping
   really keep the source application focused on GNOME and KDE? If not, the fallback is to show the window only
   after the selection ends and accept that the compositor may focus it, disclosed in the UI.
2. Whether click-to-focus reliably grants keyboard focus to a frameless `Qt::Tool` window on each compositor, or
   whether the window must be recreated as a normal toplevel on click.
3. Whether `Qt::WindowStaysOnTopHint` produces usable behaviour anywhere; it is treated as best effort and the
   design does not depend on it.
4. Clipboard write permissions when the window has just been focused on Wayland (`QClipboard` timing); verify the
   copy action works on the first click on each target.
5. Whether the original-text disclosure is worth its screen space at 125 % scaling on small laptops.
